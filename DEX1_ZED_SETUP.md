# Dex1_1 and ZED Mini on SONIC V1.1

Software integration is installed and tested locally. **Physical operation has
not been verified:** on 2026-09-12 the ZED SDK enumerated no cameras, no video
devices were present, and `enP2p1s0` (192.168.123.222) was down. No physical
motor commands or calibration commands were sent.

## ZED Mini RGB camera

From this repository:

```bash
./run-zed-camera.sh
```

The camera server publishes the rectified **left RGB image** as `ego_view`
over SONIC's existing ZMQ/msgpack/JPEG protocol on port 5555. Configure SONIC's
camera client with this machine's reachable IP and that port. Default capture
is HD720 at 30 FPS. Select a particular camera by serial number:

```bash
./run-zed-camera.sh --ego-view-device-id YOUR_SERIAL
```

Other options: `--zed-view right`, `--zed-flip`, `--zed-resolution HD1080`.
This integration supplies the RGB view consumed by the existing VLA/camera
clients. It does not add a depth stream or a binocular headset video protocol.
The ZED is not needed by the low-level SONIC locomotion policy itself.

The existing ZED SDK 5.4.1 is used with its ARM64 `pyzed` 5.4 wheel in
`.venv_camera` (Python 3.12). This is separate from `.venv_sim`: the ZED wheel
requires NumPy 2, whereas the SONIC simulation package pins NumPy 1.26.4.
The camera environment has no Torch dependency. Its dependency check passes.

Read-only detection:

```bash
.venv_camera/bin/python -c 'import pyzed.sl as sl; print(sl.Camera.get_sdk_version()); print(sl.Camera.get_device_list())'
```

## Choose the Dex1 wiring explicitly

| C++ flag | Wiring | Command transport |
| --- | --- | --- |
| `--hand-type dex1-internal` | Internally wired G1-29 | Existing `rt/lowcmd`, indices **31 left / 33 right**, CRC computed after inserting gripper commands |
| `--hand-type dex1` | External serial-to-DDS service | `rt/dex1/left/cmd`, `rt/dex1/right/cmd`, `unitree_go/MotorCmds_` |
| `--hand-type dex3` | Original Dex3 hands | Original backend; remains the default |
| `--hand-type none` | No hand control | No hand command publishing |

The internal path uses SONIC's existing body-command writer. **Do not run
`xr_teleoperate`'s arm/body controller alongside SONIC:** both would publish
body commands. Its gripper integration was used as a protocol reference,
not started as another robot controller.

External wiring requires the [Unitree Dex1 service](https://github.com/unitreerobotics/dex1_1_service)
on the computer connected to the gripper serial ports. That service was not
installed or started here; the appropriate path depends on your wiring.
Internal wiring does not require that service.

Read-only state check, substituting the correct hand type:

```bash
.venv_sim/bin/python gear_sonic/scripts/check_dex1.py \
    --interface enP2p1s0 --hand-type dex1-internal
```

Receiving low-state slots alone does not establish that internal grippers are
present or calibrated. Confirm wiring and closed/open encoder positions before
the supported first-motion test.

## Hand command mapping

The SONIC policy and existing teleop/VLA input packets retain their original
29 body joints and 7-value hand vectors. The Dex1 adapter extracts a scalar
closure from the SONIC index-distal hand target (`left: -q[4]/1.5`,
`right: q[4]/1.5`, clamped to [0,1]). This matches the index/middle/ring
presets generated by `G1GripperInverseKinematicsSolver` and VLA hand helpers:
zero hand pose means open; a full grip means closed. Arbitrary dexterous-hand
retargeting vectors are not a calibrated Dex1 grasp representation.

Physical targets follow the `xr_teleoperate` reference: **0 rad closed,
5.4 rad open**, Kp **5.0**, Kd **0.05**, zero feedforward torque and velocity.
Targets are clamped within 0.18 rad of feedback, with an additional 36 rad/s
command-slew limit. The existing max-close-ratio limit also applies.

- Without valid hand input, hold the measured gripper position; do not reuse
  the original Dex3 default closed pose or its startup open/close sequence.
- Missing, nonfinite, out-of-range or older-than-250-ms gripper feedback
  disables the corresponding command. Shutdown removes position stiffness.
- Input availability comes from SONIC's existing input interface; this does
  not add a new transport-level watchdog to every teleop/VLA input source.
- Robot metadata includes `hand_type`. For Dex1, logged hand q/dq/action
  slot 0 contains the physical gripper value; the other six slots are zero.
  Dataset consumers must interpret those fields using `hand_type`.

The unchanged SONIC model was released for the G1 configuration in the repo.
Successful software tests do not validate changes in hand mass, grasp force,
calibration, collisions or whole-body stability on your particular robot.

## Physical controller launcher

Only run after hardware bring-up with the robot supported and emergency stop
available. **Launching the controller starts its standing initialization; `]`
is not a guard against all startup body movement.**

```bash
./run-sonic-hardware.sh enP2p1s0 dex1-internal
# Or, for external service wiring:
./run-sonic-hardware.sh enP2p1s0 dex1
```

The launcher requires an explicit hand type and an active physical interface,
uses SONIC V1.1 with the documented ankle gains, retains CRC checking and
selects `zmq_manager` for the existing teleop/VLA input stream. It does not
start a headset streamer, VLA model server or camera server automatically.
The existing simulation launcher still defaults to Dex3 because its MuJoCo
model has Dex3 hand geometry.

## Verification and maintenance

The C++ Release build succeeds. Four gripper tests cover grip direction,
feedback limits, preserving every non-gripper command slot, startup hold,
shutdown, invalid/stale feedback and external DDS exchange on **loopback,
domain 141**. Five camera tests use a fake SDK device to verify SDK selection,
RGB channel order, frame ownership, serialization and error handling.
Hardware SDK import/enumeration was real; image capture could not start
without a connected camera.

The modified controller also ran with `--hand-type dex1-internal` against
headless MuJoCo over loopback. Twenty consecutive body-command frames had
finite body targets, the expected Dex1 slots/gains and valid CRCs. The stock
simulator does not model Dex1 jaw dynamics, so this verifies command
integration rather than physical gripper motion.

```bash
source sonic-env.sh
cmake --build gear_sonic_deploy/build -j 6
gear_sonic_deploy/target/release/dex1_hands_test
.venv_camera/bin/python -m pytest gear_sonic/tests/test_zed_camera.py -q
```

The gripper validation deliberately checks nonfinite values using IEEE bit
patterns: the repo's `-ffast-math` build can optimize away `std::isfinite`.

## Dex1 side swap (added 2026-09-16)

Unitree's `dex1_1_service` names each gripper by MOTOR ID (id 0 -> `rt/dex1/left`,
id 1 -> `rt/dex1/right`). On this robot the id-0 motor is on the RIGHT arm, so the
physical right gripper answers on `rt/dex1/left`. The controller now takes
`--dex1-swap-sides`, which exchanges the two sides in the Dex1 adapter (external
topics and internal motor slots alike) so the policy's left/right stay physical:

```bash
./run-sonic-hardware.sh enP2p1s0 dex1 --dex1-swap-sides
```

Verify before the first motion: `scripts/dex1_selftest.py --only-read --topic-side left`
in `~/Documents/G1_VLM_C` reports the right-arm gripper's angle.

Installed the same day: `.venv_teleop` (`install_scripts/install_pico.sh`) and
`.venv_data_collection` (`install_scripts/install_data_collection.sh`). The
XRoboToolkit onboard service still needs
`sudo dpkg -i gear_sonic_deploy/thirdparty/roboticsservice_1.0.0.0_arm64.deb`.
